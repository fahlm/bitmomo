# Bitmomo Intelligence Products — Failure Mode Matrix

**Scope:** for each named failure mode in `bitmomo-regime` (Product A) and `bitmomo-watchtower`
(Product B), this matrix states what actually happens today, traced against the real code —
not a hoped-for design. Every row cites the class/method that determines the answer. Five
columns, per the brief:

- **FAIL CLOSED?** — on this failure, does the plugin refuse to produce/persist a result
  (safe) or does it silently proceed with something wrong (unsafe)?
- **STATE PRESERVED?** — is prior persisted state left untouched, or can this failure mode
  corrupt/duplicate it?
- **PUBLIC OUTPUT?** — does anything reach a public-facing surface (Regime's shortcodes are
  the only public surface either plugin has — Watchtower has none at all: private CPTs,
  admin-only diagnostics, no shortcode, no REST route)?
- **ALERT?** — does this failure mode itself produce a Watchtower alert? (N/A for every
  Regime row — Product A has no alerting mechanism of its own.)
- **ADMIN VISIBILITY?** — can a human notice this happened via the plugin's own admin
  diagnostics screen, or only by inspecting logs/database directly?

## Product A — `bitmomo-regime`

| Failure mode | FAIL CLOSED? | STATE PRESERVED? | PUBLIC OUTPUT? | ALERT? | ADMIN VISIBILITY? |
|---|---|---|---|---|---|
| Missing input (a required field absent from raw input) | **Yes** — `Bitmomo_Regime_Input::validate()` rejects before classification ever runs; `Bitmomo_Regime_State_Store::evaluate_and_record()` returns `{success:false, errors, record:null}` immediately | **Yes** — nothing is written; the previous official record is untouched | Unaffected — `[bitmomo_market_regime]` keeps showing the last successfully persisted record (or the honest "No regime data yet" state if none exists) | N/A | **No** — this is the matrix's clearest gap. A rejected evaluation is returned to the caller (Codex's scheduled job) but is **never persisted anywhere**; `Bitmomo_Regime_Admin_Diagnostics` only reads persisted `bm_regime_state` records, so a run that failed validation leaves zero trace in the admin screen. Only visible if Codex's own scheduler logs the returned `errors` array somewhere outside this plugin. |
| Stale source (the feed's `as_of` is old, but the record is otherwise well-formed) | **No** — `Bitmomo_Regime_Input::validate()` has no freshness/format check on `as_of` at all (see `FIELD_SEMANTICS.md`); a stale record validates and classifies identically to a fresh one | N/A — a normal new record is appended | **Yes, silently** — the shortcode has no concept of staleness either; it renders whatever `get_latest()` returns as if it were current | N/A | **Partial** — `as_of` is stored and shown on the admin diagnostics screen, so a human who checks could notice it looks old, but nothing flags or highlights staleness automatically. |
| Duplicate source record (the same `source_record_id`/input submitted twice, e.g. a scheduler double-fire) | **No** — there is no dedup check by `source_record_id` or `as_of` anywhere in `evaluate_and_record()`; append-only means every call creates a new post regardless of whether an identical one already exists | **Technically yes** (nothing is overwritten) **but duplicated** — two near-identical records now exist | `get_latest()` is unaffected (returns the newest either way) but **`[bitmomo_market_regime_history]` IS affected** — see the `Bitmomo_Regime_History` note below | N/A | The duplicate is visible in the admin diagnostics screen's raw record list (nothing hides it), but nothing flags "this looks like a duplicate of the record above it." |
| Ambiguous regime (classifier lands on `TRANSITION`) | **N/A — this is a designed, not a failure, outcome.** `Bitmomo_Regime_Classifier::evaluate()` deliberately returns `TRANSITION` (with a capped, lower confidence — see `Bitmomo_Regime_Config::TRANSITION_CONFIDENCE_CEILING=65`) rather than forcing a guess when `MIN_CLASSIFICATION_SCORE` or `TRANSITION_MARGIN` isn't cleared. This is the classifier failing closed on confidence, by design (see the `regime-transition.json` fixture). | Yes — persisted like any other record | Yes — shown as `Transisi`/`Transition` on the card, same as any other regime | N/A | Yes — evidence/conflicts are fully persisted and visible in admin diagnostics, same as a clear regime. |
| Classifier version change (`Bitmomo_Regime_Config::CLASSIFIER_VERSION` bumped, e.g. thresholds retuned) | **Partially fail-closed** — old records keep their original `classifier_version` stamp forever (never rewritten — append-only), so history never silently changes meaning. But nothing in `Bitmomo_Regime_History`/the shortcodes checks for a version boundary crossing a displayed history window — a 7/14/30-day view can silently mix records produced by two different classifier versions with no visual distinction. | Yes — old records are immutable | **Ambiguous** — the history list can blend two classifier eras with no indication to the viewer | N/A | Admin diagnostics shows `classifier_version` per record (so a human inspecting closely can tell), but there is no summary/warning that "this history spans a classifier version change." |
| Scheduler runs twice (e.g. a cron double-fire triggers `evaluate_and_record()` twice for what should be one evaluation) | **No** — same root cause as "duplicate source record" above; nothing prevents or detects two evaluations in quick succession | Two records are appended instead of one | **Yes — this directly corrupts the "N of 30 days" framing.** `Bitmomo_Regime_History::for_frontend()` treats "last N *records*" as "last N *days*" with no calendar-day bucketing or dedup at all (confirmed by reading `for_frontend()`/`project()` — there is no date-collapsing logic anywhere in that class). Two evaluations on the same calendar day become two entries in the history list, and `available_days`/`target_days` both silently overcount actual elapsed days. | N/A | The duplicate pair is visible in admin diagnostics as two separate timestamped records, but nothing flags them as same-day duplicates. |
| History incomplete (fewer than `TARGET_DAYS=30` records exist yet, e.g. the plugin was just activated) | **Yes — this is explicitly designed to fail closed/honest.** `Bitmomo_Regime_History::for_frontend()` never fabricates missing days; `available_days` reports the true count and the shortcode prints an explicit "Showing N of 30 days — history is still accumulating" note (see `class-bitmomo-regime-shortcodes.php::render_history()`). | N/A — nothing to preserve yet | Yes, honestly labeled as incomplete | N/A | Yes — same record count is what admin diagnostics would show too. |

## Product B — `bitmomo-watchtower`

| Failure mode | FAIL CLOSED? | STATE PRESERVED? | PUBLIC OUTPUT? | ALERT? | ADMIN VISIBILITY? |
|---|---|---|---|---|---|
| Malformed event (a raw event candidate missing a required field, wrong type, out-of-range score, etc.) | **Yes** — `Bitmomo_Watchtower_Event_Input::validate()` rejects outright, returns `{valid:false, errors, input:null}`; nothing downstream (materiality, dedup) ever sees it | Yes — nothing is scored or persisted | N/A — Watchtower has **no public output surface at all** (private CPTs only, `manage_options`-gated admin screen, no shortcode, no REST route) | No | **No** — same gap as Regime's missing-input case: a rejected event candidate is returned to whatever detector/caller submitted it, but nothing in this plugin persists a record of the rejection. There is currently no "failed event ingestion" log visible in `Bitmomo_Watchtower_Admin_Diagnostics`. |
| Duplicate event (multiple detector reports of the same underlying real-world event) | **N/A — this is the designed, not a failure, case.** `Bitmomo_Watchtower_Deduplicator::cluster()` exists specifically to absorb this: same `event_type` within `CLUSTER_WINDOW_MINUTES` (30) of the cluster's rolling `last_seen` becomes one cluster with `member_count > 1`, not N separate alerts (see the Task 4 fixtures' `expected_dedup_behavior` blocks for worked examples). | Every input candidate is preserved inside the cluster's `members` list — never dropped, never merged away | N/A (no public surface) | Only the cluster's `representative` (highest-scoring member) would ever inform a downstream alert decision, once a synthesis step exists — see `BITMOMO_RUNTIME_DATAFLOW.md`'s note that no such synthesis step is built yet | Full member list including every duplicate is preserved in the cluster structure — nothing hidden. |
| Feed missing (no detector has reported anything for an extended period) | **N/A — undetectable by this plugin today.** There is no heartbeat/liveness concept anywhere in `bitmomo-watchtower` — the plugin has no way to distinguish "nothing happened" from "the detector stopped running." This is a real, reportable gap: `context['data_quality_degraded']` (which drives the `DATA_DEGRADED` transition) must be supplied by an upstream caller that itself noticed the feed is missing — Watchtower cannot infer this from silence alone. | N/A | N/A | **No alert is possible without an external caller noticing and passing the flag** — this is a genuine blind spot for Codex's runtime design to account for. | No — nothing to show, because nothing is detected. |
| Price source stale | Same as Regime's "stale source" row — **no freshness check exists in `Bitmomo_Watchtower_Event_Input` or `Bitmomo_Watchtower_Thesis`.** A stale-but-well-formed candidate validates and scores normally. Detecting staleness and setting `context['data_quality_degraded']` is entirely an upstream/Codex responsibility. | N/A | N/A (no public surface) | No, unless an upstream caller explicitly flags it | No automatic flag; only visible if `data_quality_degraded` is explicitly set and the resulting `DATA_DEGRADED` transition/alert is inspected. |
| Thesis missing (no thesis has ever been persisted — first-ever evaluation) | **Yes, explicitly handled, not an error.** `Bitmomo_Watchtower_State_Transition_Engine::evaluate()` checks `null === $previous_thesis` at priority step 2 (right after the `data_quality_degraded` override) and returns `THESIS_CHANGE` with reason "No previous thesis exists — establishing the initial thesis." — a clean, designed bootstrap path, not a fail-closed rejection. | The first thesis is persisted normally via `Bitmomo_Watchtower_Thesis_Store::set_current()` | N/A (no public surface) | **Yes** — `THESIS_CHANGE` maps to `ALERT_CLASS_THESIS_CHANGE`, which is NOT cooldown-exempt but has no prior alert to be in cooldown against, so the very first thesis always alerts | Yes, immediately visible as the first row in admin diagnostics' thesis history. |
| Outbox send failure (a future Telegram adapter attempts delivery and fails) | **Partially fail-closed, but entirely dependent on code that doesn't exist yet.** `Bitmomo_Watchtower_Alert_Outbox::mark_status($id, 'failed', $note)` exists as the documented target for this (see `CODEX_INTEGRATION_CONTRACT.md`), but **nothing in either plugin ever calls it** — there is no send transport built. As designed, a `mark_status('failed', ...)` call would update `status` and record an optional `status_note`, but it does **not** retry, re-queue, or otherwise recover the alert automatically — `mark_status()` never transitions a record back to `queued`. | The alert record itself is preserved regardless of status (append-only CPT, never deleted) | N/A (no public surface) | The alert was already "sent" (attempted) by definition of reaching this failure mode — this is about delivery failure, not alert-decision failure | **Yes, if `mark_status()` is ever actually called** — `status`/`status_note` are both in `Bitmomo_Watchtower_Admin_Diagnostics`' visible field set via `get_recent()`. But since nothing calls `mark_status()` today, a send failure by a not-yet-built adapter has no real-code behavior to verify — this row describes the contract, not tested behavior. |
| Cooldown conflict (two same-class transitions compete for one cooldown window) | **By design, fails closed toward "don't spam," not toward "don't miss."** See `ALERT_POLICY_SAFETY_REVIEW.md` for the full review — the second, suppressed alert is dropped (not queued, not retried) once `Bitmomo_Watchtower_Alert_Policy::evaluate()` returns `should_alert:false`. Two documented ambiguities apply here directly: no severity-based bypass within a class, and cooldown is not domain-scoped (a `market`-domain and `derivatives`-domain event of the same alert class share one clock). | The underlying thesis transition itself is still recorded via `Bitmomo_Watchtower_Thesis_Store::set_current()` regardless of whether an alert fires — only the ALERT is suppressed, not the state change | N/A (no public surface) | **No** — the suppressed alert never reaches the outbox at all (`Bitmomo_Watchtower_Orchestrator::process()` only calls `enqueue()` when `alert_decision['should_alert']` is true) | The underlying thesis change is visible in thesis history either way; the fact that an alert was *suppressed* (as opposed to never having been warranted) is **not** separately recorded anywhere — admin diagnostics cannot currently distinguish "no alert because NO_CHANGE" from "no alert because cooldown suppressed a MATERIAL_CHANGE." |
| Data degraded (`context['data_quality_degraded']` set) | **Yes, and deliberately the strongest override in the whole engine** — checked first, before even the "no previous thesis" bootstrap case; overrides every other classification regardless of what the thesis diff looks like | The new (possibly-unreliable) thesis is still persisted via `Bitmomo_Watchtower_Thesis_Store::set_current()` (any non-`NO_CHANGE` transition persists) — so a degraded-data evaluation DOES become part of history, just clearly labeled `DATA_DEGRADED` in its transition record/alert | N/A (no public surface) | **Yes, always** — `DATA_QUALITY` is one of the two `COOLDOWN_EXEMPT_ALERT_CLASSES`, so this alerts every time regardless of recent alert history | Yes — both the persisted thesis record and the alert (with `alert_class: DATA_QUALITY`) are fully visible in admin diagnostics. |

## Cross-cutting gaps this matrix surfaces (not fixed here — reporting only)

1. **Neither plugin persists a record of a REJECTED input.** A missing-required-field failure
   in either `Bitmomo_Regime_Input::validate()` or `Bitmomo_Watchtower_Event_Input::validate()`
   is returned to the caller and then vanishes — no admin screen shows "N evaluations failed
   validation this week." If Codex's scheduled job doesn't itself log these, they are
   invisible.
2. **Neither plugin has any staleness/freshness detection of its own.** Both rely entirely on
   an upstream caller noticing stale data and (for Watchtower) explicitly setting
   `context['data_quality_degraded']`. Regime has no equivalent flag at all — a stale Regime
   evaluation is indistinguishable from a fresh one anywhere in the plugin.
3. **`Bitmomo_Regime_History` has no day-bucketing or dedup** — "N of 30 days" is actually "N
   of the last 30 *records*," which silently overcounts if the scheduler ever double-fires.
4. **Watchtower's admin diagnostics cannot distinguish "no alert needed" from "alert
   suppressed by cooldown."** Both look identical from the outside (no new outbox entry).
